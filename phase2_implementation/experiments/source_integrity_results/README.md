# Completion and duplicate-record investigation

The source construction was replayed in memory with ordinary CSV writes disabled. A second construction replaced conflicting duplicate fields with unknown values before retaining one record per key. This is a conservative sensitivity rule, not proof that every conflicting answer is wrong. Individual-level reconstruction files stay under ignored data/processed/source_integrity_audit; only aggregate evidence belongs here.

No current dropout had an unknown or invalid completion code. There were 67 completed-basic exclusions in the training baseline and 127 in the later baseline. Conservative duplicate handling preserved all 1,307 training and 1,395 later labelled children and every outcome. It changed one training English score and no later inputs. That same score was already missing in the earlier corrected dataset. Thus no new label correction was identified in these two specific concerns. This does not prove all outcome labels or identity matches are error-free.

Six fixed model families were compared on identical five-district-grouped folds, repeated with seeds 42, 137 and 293, for 180 fits. Only training data were used for model evaluation. Preprocessing was refitted inside each fold; all validation children remained eligible. The policy selects 20 percent within each fold. These uncalibrated fixed-setting comparisons are not the frozen tuned/calibrated temporal evaluation and cannot replace its results.

LightGBM caught exactly one additional dropout per repetition (mean 61 to 62 of 188), with one fewer false alarm. Precision rose from 23.49% to 23.88%, recall from 32.45% to 32.98%, and F1 from 27.25% to 27.70%. Random Forest changed from 75.67 to 76.33 caught on average. Extra Trees changed from 77 to 75.67; XGBoost from 62.33 to 61.67; ElasticNet was unchanged and CatBoost varied across repetitions. Three repetitions reuse the same children and do not constitute independent confirmation.

The isolated correction produces small, model-dependent changes, not a demonstrated substantial or deployment-ready improvement. No model is promoted and no original dataset is overwritten. Retain source-supported uncertainty handling for data integrity, not because a score happens to improve. Fresh prospective measurements and a genuinely independent evaluation would be needed to test further improvement credibly; their benefit is not guaranteed.

Reproduction: run source_integrity_audit.py, then source_integrity_evaluation.py with the project Python environment. The audit covers first-record duplicate operations used by the core dataset-building notebook through cell 27 and completion status among labelled dropouts. It does not comprehensively resolve every possible source-data quality issue.
